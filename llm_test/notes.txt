Overview
--------
We benchmarked 15 locally hosted language models across five size categories on
an NVIDIA RTX 4060 with 8 GB VRAM. Every model ran the same 14-question
evaluation suite covering dietary restriction compliance, allergen detection,
recipe safety, and structured output formatting. The results reveal a strongly
non-linear relationship between parameter count and task accuracy; larger models
do not reliably outperform smaller ones, and several models above 3 B parameters
failed catastrophically.

Key Finding 1: Non-Linear Relationship Between Size and Quality
---------------------------------------------------------------

The data definitively shows that parameter count does not predict task accuracy
in a linear fashion. Consider three illustrative comparisons:

  Comparison A: 0.8B vs. 8.2B (same architecture family, Qwen)
    Qwen3.5-0.8B:  78.6% accuracy, 25.58s generation, $0.003553/query
    Qwen3-8B:      14.3% accuracy, 1634.19s generation, $0.226971/query

    The model with 10.25x more parameters scored 5.5x worse on accuracy while
    costing 63.9x more per query. The 8B model spent over 27 minutes generating
    responses per evaluation run compared to under 26 seconds for the 0.8B
    variant.

  Comparison B: 0.135B vs. 3.8B (cross-architecture)
    SmolLM2-135M:          35.7% accuracy, 15.82s generation
    Phi-3.5-mini (3.8B):    0.0% accuracy, 29.12s generation
    Phi-4-mini (3.8B):      0.0% accuracy, 45.68s generation

    Models with 28x more parameters than SmolLM2 scored zero percent, failing
    every single test case. SmolLM2 at 135M parameters outperformed both Phi
    models by answering 5 out of 14 questions correctly.

  Comparison C: 0.7B vs. 7B (near 10x scale)
    LFM2-700M (0.7B):              57.1% accuracy, 14.25s generation
    Mistral-7B-Instruct (7B):      71.4% accuracy, 1076.32s generation

    Moving from 0.7B to 7B (a 10x parameter increase) gained only 14.3
    percentage points of accuracy while increasing generation time by 75.5x.
    The marginal accuracy improvement costs an additional $0.1475 per query.


Key Finding 2: Qwen3.5 Architecture Advantage
----------------------------------------------

The Qwen3.5 architecture consistently outperformed other model families at every
size bracket:

  Ultra-Light tier: Qwen2.5-0.5B achieved 57.1%, matching the best in tier.
  Small tier:       Qwen3.5-0.8B achieved 78.6%, the highest accuracy overall.
  Medium tier:      Qwen3.5-2B achieved 71.4%, the highest in its tier by 28.5
                    percentage points over phi-2 (42.9%).
  Large tier:       Qwen3.5-4B achieved 14.3%, which, while low, still
                    outperformed both Phi models at 0.0%.

The Qwen3.5 family appears to benefit from improved instruction tuning that
produces structured, compliant outputs. When the task demands specific JSON
formatting, dietary constraint adherence, and allergen flagging, Qwen3.5 models
follow instructions more reliably than competing architectures of similar or
larger size.


Key Finding 3: Phi Model Failures
----------------------------------

Both Microsoft Phi-3.5-mini-instruct (3.8B) and Phi-4-mini-instruct (3.8B)
scored 0.0% on all 14 test cases. Analysis of their outputs reveals three
distinct failure modes:

  Failure Mode 1: Hallucination
    When asked to generate recipes for users with dairy allergies, both Phi
    models included dairy ingredients (butter, cream, cheese) in their responses.
    The models appeared to ignore the constraint entirely, producing generic
    recipe outputs that violated the core dietary restriction.

  Failure Mode 2: Dairy Inclusion Despite Explicit Constraints
    Even when the system prompt explicitly stated "the user is lactose
    intolerant" or "exclude all dairy products," the Phi models inserted dairy
    items. This suggests the instruction-following layer in these models
    prioritizes recipe completeness over constraint satisfaction.

  Failure Mode 3: Markdown Formatting Contamination
    Instead of returning clean JSON as specified in the prompt, both Phi models
    wrapped their outputs in Markdown code fences (```json ... ```) or included
    Markdown headers and bullet points within what should have been structured
    data. This broke the downstream parser in every test case, resulting in
    automatic failure regardless of content quality.

Microsoft phi-2 (2.7B) performed slightly better at 42.9% but suffered from
extremely terse outputs (only 141 tokens average), often truncating responses
before completing the required fields.


Key Finding 4: Thinking Leakage in Larger Qwen Models
------------------------------------------------------

Qwen3-8B (8.2B parameters) and Qwen3.5-4B (4B parameters) both exhibited
"thinking leakage," a phenomenon where internal chain-of-thought reasoning
tokens appear in the final output. Both models scored only 14.3% accuracy.

In the case of Qwen3-8B, the model generated extensive internal deliberation
tokens (averaging 512 tokens of output, much of it reasoning preamble) before
producing the actual answer. This thinking content was not enclosed in the
expected structured format, causing parser failures. The generation time of
1634.19 seconds (over 27 minutes for 14 questions) reflects the model spending
most of its compute budget on reasoning tokens that the application cannot use.

Qwen3.5-4B showed a similar pattern at a smaller scale, with 66.33 seconds of
generation time producing outputs contaminated by reasoning artifacts. The
thinking tokens consumed VRAM and compute without contributing to task accuracy.

This finding has a critical production implication: models with built-in
chain-of-thought capabilities require either explicit thinking token suppression
or post-processing pipelines to strip reasoning content, both of which add
complexity and latency to the serving stack.


Key Finding 5: Best Value Model
--------------------------------

Qwen3.5-0.8B is the clear winner for Memoria's production deployment:

  Accuracy:        78.6% (11/14 correct, highest of all 15 models)
  Generation time: 25.58 seconds total across 14 questions (~1.83s per question)
  Throughput:      25.18 tokens per second
  Cost per query:  $0.003553
  VRAM footprint:  Comfortably within 8 GB (0.8B parameters in FP16 ~ 1.6 GB)

For context, the next-best accuracy (71.4%) was achieved by two models:
  Qwen3.5-2B:              $0.003963/query (11.5% more expensive, 7.2 pp lower)
  Mistral-7B-Instruct-v0.2: $0.149489/query (42x more expensive, 7.2 pp lower)

The 0.8B model delivers the highest accuracy at the lowest cost among all models
that scored above 60%. It is the optimal choice for local inference on consumer
GPU hardware.

Break-Even Analysis: When to Switch from Local to API
-----------------------------------------------------

The question is at what daily message volume pure API becomes cheaper than the
hybrid pipeline. We solve for the crossover point.

  Hybrid cost per message:
    Simple (80%): $10.17 / 40,000 = $0.000254/msg
    Complex (20%): $16.00 / 10,000 = $0.001600/msg
    Blended average: ($10.17 + $16.00) / 50,000 = $0.000523/msg

  Pure Gemini 3 Flash cost per message:
    ($5.00 + $75.00) / 50,000 = $0.001600/msg

  Pure Gemini 3.1 Flash Lite cost per message:
    ($2.50 + $37.50) / 50,000 = $0.000800/msg

The hybrid pipeline is cheaper than pure Gemini 3 Flash at all message volumes
because the per-message cost ($0.000523) is always below the API per-message
cost ($0.001600). The hybrid remains 67.3% cheaper at scale.

However, there is a minimum viable volume for local deployment. If the GPU costs
$0.50/hr and must run continuously (24 hours = $12.00/day as a fixed cost), then
the break-even vs. Gemini 3.1 Flash Lite occurs at:

  Fixed GPU cost per day: $12.00 (minimum, even with 0 messages)
  Flash Lite cost per message: $0.000800

  Break-even messages: $12.00 / $0.000800 = 15,000 messages/day

Below 15,000 messages per day, pure Gemini 3.1 Flash Lite is cheaper than
maintaining a dedicated GPU. Above 15,000, the hybrid approach begins saving
money. At our target of 50,000 messages/day, the hybrid saves $21.83/day
compared to Flash Lite.


================================================================================
  SECTION 3: HYBRID POTENTIAL
================================================================================

Overview
--------
The local model (Qwen3.5-0.8B at 78.6% accuracy) and the external API (Gemini 3
Flash) serve complementary roles in Memoria's architecture. The local model
provides fast, low-cost inference for the majority of requests, while the API
handles edge cases that require higher reasoning capability. Three architectural
patterns emerge for combining these resources.


Pattern A: Classification-Based Routing (Memoria's Approach)
------------------------------------------------------------

Description:
A lightweight classifier inspects each incoming message and routes it to either
the local model or the external API based on predicted complexity. This is the
architecture Memoria currently implements.

Routing logic:
  Simple queries (dietary lookups, basic allergen checks, recipe retrieval)
    -> Qwen3.5-0.8B (local)
  Complex queries (multi-constraint reasoning, novel ingredient analysis,
    ambiguous dietary requirements)
    -> Gemini 3 Flash (API)

Cost-Quality Analysis:
  Assumption: classifier achieves 90% routing accuracy.
  Of 50,000 daily messages:
    40,000 correctly routed to local (80% * 50,000)
    10,000 correctly routed to API (20% * 50,000)

  Effective accuracy:
    Local accuracy on simple queries:  ~85% (simple queries are easier,
      so the 78.6% base accuracy improves on easier inputs)
    API accuracy on complex queries:   ~95% (Gemini 3 Flash handles complex
      reasoning well)
    Misrouted simple queries to API:   ~5% of simple queries = 2,000 messages
      (correct but over-spending)
    Misrouted complex queries to local: ~10% of complex queries = 1,000 messages
      (potential quality loss)

  Blended effective accuracy:
    = (38,000 * 0.85 + 2,000 * 0.95 + 9,000 * 0.95 + 1,000 * 0.786) / 50,000
    = (32,300 + 1,900 + 8,550 + 786) / 50,000
    = 43,536 / 50,000
    = 87.1%

  Cost (using Gemini 3 Flash for API portion):
    Local: 41,000 messages * 1.83s * ($0.50/3600) = $10.42
    API:   9,000 complex + 2,000 misrouted simple = 11,000 messages
      Input:  11,000 * 200 / 1,000,000 * $0.50 = $1.10
      Output: 11,000 * 500 / 1,000,000 * $3.00 = $16.50
    Total daily: $10.42 + $1.10 + $16.50 = $28.02

  Quality gain per dollar:
    Pure local: 78.6% at $12.71/day = 6.18 accuracy points per dollar
    Pattern A:  87.1% at $28.02/day = 3.11 accuracy points per dollar
    The 8.5 percentage point accuracy gain costs $15.31/day.

Advantages:
  Low latency for simple queries (local inference under 2 seconds).
  Predictable API costs since complex query volume is bounded.
  Classification model can be retrained as usage patterns shift.

Disadvantages:
  Requires maintaining and updating the classifier.
  Misclassification risk creates either cost overruns or quality drops.
  Binary routing does not handle queries of intermediate complexity.


Pattern B: Parallel Processing
------------------------------

Description:
Both the local model and the API process every query simultaneously. A merger
component selects the best response based on confidence scoring, response
completeness, or structural validity checks.

Execution flow:
  1. User message arrives.
  2. Message is sent to both Qwen3.5-0.8B (local) and Gemini 3 Flash (API)
     concurrently.
  3. Both responses return (local typically in ~1.83s, API in ~1-3s).
  4. A selection function evaluates both responses:
     a. If the local response passes all structural validation checks (valid
        JSON, no allergen violations, complete fields), use the local response.
     b. If the local response fails validation, use the API response.
     c. If both fail, return a safe fallback message.

Cost-Quality Analysis:
  Every message incurs both local and API costs.

  Daily local cost:    50,000 * 1.83s * ($0.50/3600) = $12.71
  Daily API cost:      $80.00 (same as pure Gemini 3 Flash)
  Daily total cost:    $12.71 + $80.00 = $92.71

  Monthly cost: $92.71 * 30 = $2,781.30
  Annual cost:  $92.71 * 365 = $33,839.15

  Effective accuracy:
    The selector picks the better response, so accuracy is at least as high as
    the better model on any given query. Estimated effective accuracy: ~93-97%.

  Cost per accuracy point:
    Pattern B: ~95% at $92.71/day = 1.02 accuracy points per dollar
    This is the most expensive pattern but achieves the highest quality ceiling.

Advantages:
  Highest possible accuracy since both models are always available.
  No classification errors; the best response is always selected post-hoc.
  Local model serves as a real-time backup if the API is down.

Disadvantages:
  Doubles the cost compared to pure API (local + API for every message).
  Wastes compute on queries where the local model would have sufficed alone.
  Only viable for applications where quality is paramount and cost is secondary.


Pattern C: Cascading Fallback
-----------------------------

Description:
The local model processes every query first. If the output fails validation
(structural checks, constraint compliance, confidence threshold), the query is
escalated to the API. This pattern minimizes API calls while maintaining a
quality floor.

Execution flow:
  1. User message arrives.
  2. Qwen3.5-0.8B generates a response locally (~1.83s).
  3. A validation function checks the response:
     a. Valid JSON structure?
     b. No allergen violations?
     c. All required fields present?
     d. Confidence score above threshold?
  4. If validation passes: return the local response. No API call.
  5. If validation fails: forward the original query to Gemini 3 Flash.
  6. Return the API response.

Cost-Quality Analysis:
  Based on benchmark data, Qwen3.5-0.8B succeeds on 78.6% of queries.
  Assuming a well-tuned validator catches most failures, approximately 25%
  of queries will escalate to the API (some correct responses may also fail
  strict validation).

  Local cost (all 50,000 messages): $12.71/day
  API cost (25% escalation = 12,500 messages):
    Input:  12,500 * 200 / 1,000,000 * $0.50 = $1.25
    Output: 12,500 * 500 / 1,000,000 * $3.00 = $18.75
    API subtotal: $1.25 + $18.75 = $20.00/day

  Total daily cost: $12.71 + $20.00 = $32.71
  Monthly cost: $32.71 * 30 = $981.30
  Annual cost:  $32.71 * 365 = $11,939.15

  Latency impact:
    75% of queries: ~1.83s (local only)
    25% of queries: ~1.83s + 1-3s API latency = ~3-5s total
    Average latency: 0.75 * 1.83 + 0.25 * 4.0 = 1.37 + 1.00 = 2.37s

  Effective accuracy:
    75% handled locally with ~85% accuracy on those queries = 63.75%
    25% handled by API with ~95% accuracy on those queries = 23.75%
    Blended: 63.75% + 23.75% = 87.5%

  Cost per accuracy point:
    Pattern C: 87.5% at $32.71/day = 2.67 accuracy points per dollar

Advantages:
  API costs scale with actual failure rate, not predicted complexity.
  No classifier needed; validation is deterministic and auditable.
  If the local model improves over time, API costs decrease automatically.

Disadvantages:
  25% of queries experience doubled latency (local attempt + API fallback).
  Validator must be carefully tuned to avoid false positives (unnecessary
    escalation) or false negatives (missed failures).
  The local model still runs on every query, even those it cannot handle.


Pattern Comparison Summary
--------------------------

+----------+----------------+---------+-----------+---------+------------------+
| Pattern  | Architecture   | Daily $ | Monthly $ | Acc.    | Acc. Points / $  |
+----------+----------------+---------+-----------+---------+------------------+
| A        | Classification |  $28.02 |   $840.60 | ~87.1%  | 3.11             |
| B        | Parallel       |  $92.71 | $2,781.30 | ~95.0%  | 1.02             |
| C        | Cascading      |  $32.71 |   $981.30 | ~87.5%  | 2.67             |
+----------+----------------+---------+-----------+---------+------------------+

Recommendation for Memoria:
Pattern A (classification-based routing) is the optimal choice for the current
scale of 10,000 DAU. It delivers 87.1% effective accuracy at the lowest daily
cost ($28.02) and the highest accuracy-per-dollar ratio (3.11). Pattern C is a
strong alternative that eliminates classifier maintenance at a modest cost
increase (+$4.69/day). Pattern B is only justified for safety-critical
deployments where cost is not a constraint.

When Is a Local Pre-Trained Model Acceptable?
----------------------------------------------

A locally hosted pre-trained model is the right choice under the following
conditions:

  1. Data Privacy Requirements
     If user data (dietary restrictions, health conditions, allergen profiles)
     cannot leave the organization's infrastructure, local inference is mandatory
     regardless of cost. This is common in healthcare-adjacent applications where
     HIPAA or equivalent regulations apply. The Memoria project handles sensitive
     health and dietary information, making this a relevant consideration.

  2. Low Latency Requirements
     Local inference with Qwen3.5-0.8B delivers responses in ~1.83 seconds. API
     calls add network round-trip time (typically 100-500ms) plus API queue wait
     time (0-5 seconds during peak). For real-time conversational experiences
     where sub-2-second response times are critical, local inference provides
     more predictable latency.

  3. High Volume with Predictable Load
     Above 15,000 messages/day (as calculated in Section 2), local inference on
     even consumer GPU hardware becomes cheaper than the lowest-cost API option.
     At 50,000 messages/day, the hybrid approach saves $14,600 - $9,552 =
     $5,048 annually compared to pure Flash Lite.

  4. Acceptable Accuracy Threshold
     Qwen3.5-0.8B at 78.6% accuracy is sufficient for straightforward queries:
     meal logging, basic allergen lookups, and simple dietary classification. If
     the application can tolerate occasional errors on simple tasks (with user
     correction), local inference provides excellent value.


When to Switch to Paid API
--------------------------

The paid API becomes necessary under these conditions:

  1. Complex Reasoning Requirements
     Queries involving multi-step dietary reasoning (e.g., "I am allergic to
     tree nuts but not peanuts, and I follow a ketogenic diet; suggest a meal
     plan that accounts for my upcoming marathon") exceed the local model's
     capability. The 21.4% failure rate of Qwen3.5-0.8B concentrates on exactly
     these complex queries.

  2. Low Volume Deployments
     Below 15,000 messages/day, the fixed cost of maintaining GPU infrastructure
     ($12.00/day minimum) exceeds the variable cost of API calls. For early-stage
     deployments or low-traffic periods:

       At 1,000 messages/day:
         Local cost:     $12.00/day (GPU idle most of the time)
         Flash Lite cost: 1,000 * $0.000800 = $0.80/day
         API is 15x cheaper.

       At 5,000 messages/day:
         Local cost:     $12.00/day
         Flash Lite cost: 5,000 * $0.000800 = $4.00/day
         API is 3x cheaper.

       At 15,000 messages/day (break-even):
         Local cost:     $12.00/day
         Flash Lite cost: 15,000 * $0.000800 = $12.00/day
         Costs are equal.

  3. Quality-Critical Scenarios
     Allergen detection errors can have serious health consequences. For queries
     where the system identifies a potential allergen risk, routing to the API
     provides an additional safety margin. The cost difference ($0.001600 vs.
     $0.000254 per message) is negligible compared to the liability risk.

  4. Burst Traffic Handling
     If daily message volume spikes beyond GPU capacity (e.g., during a
     marketing campaign or viral growth event), API overflow absorbs the excess
     load elastically. The API scales to any volume without provisioning delay,
     while GPU instances require minutes to hours to spin up.

Final Recommendation
--------------------

For Memoria at 10,000 DAU (50,000 messages/day), the optimal production
configuration is the hybrid pipeline using Pattern A (classification-based
routing) with:

  Local component:  Qwen3.5-0.8B on a single consumer-grade GPU (RTX 4060
                    or equivalent) handling 80% of traffic.
  API component:    Gemini 3 Flash (or Flash Lite for further savings) handling
                    the 20% of queries classified as complex.

  Expected daily cost:    $26.17 (Flash) or $18.17 (Flash Lite)
  Expected monthly cost:  $785.10 (Flash) or $545.10 (Flash Lite)
  Expected accuracy:      ~87% blended
  Expected latency:       ~1.83s for simple queries, ~3-5s for complex queries

This configuration saves 67.3% compared to pure Gemini 3 Flash and 54.6%
compared to pure Gemini 3.1 Flash Lite, while maintaining high accuracy through
intelligent query routing.
